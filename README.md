# Ilana's Recipes - המתכונים של אילנה

A digitization of Grandma Ilana's handwritten and clipped recipe collection (Hebrew), with a static website for browsing and searching.

Every recipe is one folder with its scans and one `recipe.json`. Nothing is invented: unreadable words are written as `[?]`, every `[?]` is explained in `uncertainties`, and anything not 100% certain is flagged `needs_human_verification`.

## Layout

```
recipes/
  batch-01/
    batch.json              batch title + description (Ilana kept recipes in batches)
    b01-r01/
      recipe.json           the transcription (see schema/recipe.schema.json)
      raw/                  the scan(s), rotated upright if needed (original name kept)
      thumb.jpg             480px thumbnail for the website grid
schema/recipe.schema.json   JSON Schema for recipe.json
tools/validate.py           validates every recipe.json and the files it references
tools/build_index.py        builds data/recipes.json (the single file the website loads)
tools/publish_prs.py        pushes one branch per recipe and opens one PR per recipe
index.html, assets/         the website (plain static files, no build step, no dependencies)
data/recipes.json           generated by tools/build_index.py - commit it after merging recipes
```

## Batch numbering

`Batch N` is the scan-folder number, not necessarily Ilana's own count. **`Batch 4` is intentionally empty**: the number 4 was skipped by mistake when folders were created (real batches go 3 -> 5), and the folder was kept to avoid renumbering. The two scans found loose in the root folder are `batch 99` (`b99-r01`). Details: `docs/BATCH_NUMBERING.md`.

## recipe.json fields

| field | meaning |
|---|---|
| `id` | `bNN-rMM` - batch number and order inside the batch |
| `title` | as written, or `null` when the card has none |
| `assigned_title` | optional editorial name for browsing/search; a string or `null`. Separate from the literal `title` |
| `source` | who/what the recipe came from (`text`, `type`: person / publication / company / unknown, `as_written`, `uncertain`) |
| `medium` | `handwritten`, `clipping` (cut from a magazine / paper / package), `printed`, `mixed` |
| `ingredients` | list of groups: `{group, items[]}` (group is `null` for an ungrouped list) |
| `instructions` | list of groups: `{group, steps[]}` |
| `notes` | additional notes on the card (and short digitization remarks, in English) |
| `incidental_text` | logos / page numbers / ads on the page that are not part of the recipe |
| `raw_files` | scans: `file`, `original_path`, `rotation_applied_cw_degrees`, `side` (single / front / back / unknown) |
| `needs_human_verification`, `confidence` | `high` / `medium` / `low` |
| `uncertainties` | each doubtful spot: `field`, `text`, `best_guess`, `reason`. A `best_guess` is never copied into the main text. |
| `transcription` | `method`, `date`, `human_verified`, `verified_by`, `verified_at` |

### Conventions

* `[?]` = a word or number that could not be read. Partly readable words are written with whatever is certain.
* Original wording, spelling and quantities are kept - typos in the source stay (a note records them).
* A card that holds two recipes becomes two recipes sharing the same scan; two scans of one recipe (front/back) become one recipe with two `raw_files`.
* Human proofreading (הגהה): fix the text, set `needs_human_verification: false`, set `transcription.human_verified: true` with your name and date, and run `python tools/validate.py`. Existing JSON field names are retained for compatibility.
* An untitled recipe keeps `title: null`. When we choose a descriptive name, store it separately in `assigned_title`; never treat it as text read from the scan or as a `best_guess` about an unreadable heading. Existing recipes can omit this field. Both titles are searchable; the original heading takes precedence for display, with the assigned title used as a clearly marked fallback.

For example, a name we choose for an untitled card would be represented as:

```json
{
  "title": null,
  "assigned_title": "עוגת תפוחים של אילנה"
}
```

This is an illustrative title, not a transcription or an assignment to any existing recipe. Assigning a title does not change transcription confidence, proofreading status, or resolve an uncertain original heading.

## Website

Open `index.html` through any static server, for example `python3 -m http.server` in the repo root and visit <http://localhost:8000>.

The site loads `data/recipes.json` and searches it in the browser: Hebrew-aware (final letters, niqqud, quotes are ignored), every word must match, title matches rank above ingredients, which rank above instructions. Filters: batch, handwritten/clipping, source, needs proofreading. Each recipe page shows the scan next to the text.

The source filter groups personal contacts under **אנשים**, and publication writers/sources under **כותבים ומקורות בפרסומים**. A source is grouped with publications when its type is `publication` or `company`, or the recipe is a clipping/printed sheet (including bylines stored as `person`). Other named sources are grouped with people. A name appearing in both categories can be filtered separately; no source attribution is changed by this grouping.

Search, filters and sorting are stored in URL parameters: `q`, `batch`, `medium`, `source`, `proofreading` (`need` or `ok`), and `sort` (`title`; the default is omitted). Copy the address bar to share a filtered list. Reloading, opening that URL in another browser, and returning from a recipe restore the same filters. Dropdown changes create browser history entries; typing updates the current entry. Unknown parameter values fall back to the default control value.

For example: `?q=עוגה&medium=handwritten&proofreading=need&sort=title#/`. Source values include their category, for example `source=person:חיה`. Recipe links still use `#/bNN-rMM`, alongside the filter parameters, so existing recipe links continue to work on GitHub Pages and Cloudflare Pages.

### Browser regression checks

Install Playwright (`pip install playwright`, then `playwright install chromium`) and run `python tools/test_website.py`. To use a system Chromium, set `CHROMIUM_PATH`, for example `CHROMIUM_PATH=/usr/bin/chromium python tools/test_website.py`. The test serves a temporary local HTTP server and checks shared/reloaded filters, navigation history, source categories, and assigned-title search/display/share behavior without changing recipe data.

### Deploy

* **GitHub Pages**: Settings → Pages → Deploy from a branch → `main` / `(root)`.
* **Cloudflare Pages**: connect the repo, framework preset "None", build command empty, output directory `/`.

After adding or merging recipes: `python tools/build_index.py` and commit `data/recipes.json`.

## Workflow

1. Each recipe is added in its own branch `recipe/bNN-rMM` and its own PR, containing only that recipe's folder.
2. PRs for transcriptions that are fully certain may be merged; everything else stays open for review.
3. `python tools/publish_prs.py --dry-run` shows what would be pushed; `python tools/publish_prs.py` pushes and opens the PRs (needs `git` push access and the GitHub CLI `gh` logged in).

The original scan folders (`Batch 1/`, `Batch 2/`, ... and loose `Scanned_*.jpg` files) are not tracked - the rotated copies under `recipes/` are the raw files.
